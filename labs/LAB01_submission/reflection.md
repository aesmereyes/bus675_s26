# Reflection: OOP Design Decisions

Write 2-3 paragraphs reflecting on your object-oriented design. Some questions to consider:

- Why did you structure your classes the way you did?
The class hierarchy in this project was built around a single guiding principle: shared behavior lives in the parent, unique behavior lives in the child. The Character base class handles what every entity in the game has in common — a name, hit points, and the ability to take damage — while Player and Enemy extend that to add combat mechanics specific to each role. From there, each playable character (ObiWan, Padme, Ahsoka, MaceWindu) inherits from Player but overrides talk() and, in some cases, attack() to reflect who they are narratively. Ahsoka attacks twice per turn because she's fast; Mace Windu's Vaapad form adds extra damage; Padmé is fragile but has a unique evidence-based win condition. The item hierarchy followed the same logic — Item → Weapon/Consumable/KeyItem → specific items like Lightsaber or BactaPatch — so that use_item() and equip_item() on the Player class could work generically using isinstance() checks rather than hardcoded item names. This made it easy to add new items without touching the core player logic.

- What was challenging about managing multiple interacting objects?
The most challenging part of the design was managing the relationships between GameEngine, Location, Player, and Combat as interacting objects. These classes constantly need to read and modify each other's state — Location.search() needs to access game_engine.current_player and game_engine.hours_remaining; Combat needs to resolve outcomes that change GameEngine.state; Player.talk() takes the game object as a parameter so dialogue can reference world state. Passing the engine around as an argument worked, but it created tight coupling that became a source of bugs, including the room description duplication issue where multiple call paths into describe_room() would fire in the same tick. A cleaner approach would have been an event system or a centralized state manager that objects emit signals to rather than calling each other directly.

- If you had more time, what would you refactor or add?

If I had more time, the first thing I would refactor is the talk() method. Right now each character class contains a large if/elif block checking location names as raw strings — if a location is renamed, every talk() method silently breaks. A better design would use a dictionary mapping location names to dialogue functions, or define dialogue as data (a JSON or YAML config) loaded at runtime, separating story content from game logic entirely. I would also add a proper DialogueNode class to support branching conversations with memory of past choices. This experience connects directly to how ML codebases are structured: a well-designed training pipeline uses the same inheritance patterns — a base Trainer class with overridable methods like train_step() or evaluate() — so that swapping a model architecture or loss function doesn't require rewriting orchestration logic. The lesson from this project is that the hard part of OOP isn't writing the classes, it's defining the right boundaries between them so that changes in one place don't cascade unexpectedly into others.

- How does this experience connect to working with OOP in analytics/ML codebases?
Working on this actually helped me understand something I'd seen in ML code but never fully clicked for me — why scikit-learn models all expose the same fit() and predict() interface even though they work completely differently under the hood. That's the same thing I was doing with Player: GameEngine just calls player.attack(enemy) or player.talk() without caring whether it's Ahsoka or Mace Windu, because the interface is consistent even though the behavior isn't. I finally get why that matters. The tight coupling problem I ran into — where Location, Combat, and Player were all reaching into each other's state — is also something I've seen cause headaches in data pipelines, where preprocessing logic ends up buried inside a model class and suddenly nothing is reusable. I didn't have a name for that problem before, but now I'd call it exactly what it is: objects knowing too much about each other. I think the reason this project made it stick is that I actually had to debug the consequences of it, not just read about it as a concept.
